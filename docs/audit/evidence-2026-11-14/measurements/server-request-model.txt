## First bottlenecks, in order

1. **Per-IP limits: 4–60 machines per office.** Key: REMOTE_ADDR + bucket (B/Filters/RateLimitFilter.php:43,73-79; B/Config/App.php:195). `device-presence` 120/min = 60 Windows PCs; `device-control-state` = 6 hosted sessions; `device-session-participants` = 4; `device-challenge/verify` 20/min = 10 PCs booting together; `portal-relay` 30/min ≈ 10 sign-ins; `signalling-token` = 90 participants (Routes.php:50-55,170-172,246-260,292-294,315-320). Browser session, control and presence polls are unlimited. A 429 is retried from 1 s and re-runs devices/me (runtime.rs:568-573). Each allowed call costs 2 reads + 2 writes of cache files, non-atomic (CI4 Throttler.php:104-135).
2. **Console outage: any load.** Once the 300 s file cache lapses, every request curls Console (2 s/4 s): the 15 s failure memo is a static, lost between requests (B/Support/ConsoleDatabaseDetails.php:223-246).
3. **Worker pool: hundreds of sessions.** Assumption: 50 ms per request and W workers give 20·W req/s ≈ 36·W browser sessions or 16·W desktop-hosted (W=20: 730 or 330).
4. **TURN lease book: ~1,500 sessions or ~2,400 idle PCs.** One JSON file under a blocking exclusive lock, rewritten per grant (K/FileLeaseStore.php:42-58,97; K/IceIssuer.php:104-111), by devices/me (B/Domain/Device/DevicePresenceService.php:167), signalling-token (B/Controllers/Api/V1/SignallingController.php:63) and device join. Measured: 9 ms per grant at 1,000 idle PCs, 44 ms at 4,000; thresholds computed from that. The agent never uses those servers (D/crates/remote-core/src/api.rs:400; session.rs:214), yet each idle PC is booked at 6 Mbit/s: measured `free_pool_full` by 70 idle PCs, so `enforce` would refuse free clients.
5. **Portal coupling: thousands of browsers.** Identity cache 60 s (B/Domain/Auth/IdentityResolver.php:24): one inline call and one upsert per browser per minute, timeouts 8 s/15 s (B/Domain/Auth/PortalClient.php:22-23), failures not cached. A slow portal pins the pool, device traffic included.
6. **Growth and scans: with time.** backend/bin/ops/jobs.txt has lifecycle and turn-probe jobs only: no purge (confirmed). Each session-hour writes 80 SIGNALLING_TOKEN_ISSUED rows (SignallingController.php:55-61); each session ~15 other events and 14 audit rows; each Windows PC 206 DEVICE_AUTHENTICATED rows a day (B/Domain/Device/DeviceAuthenticationService.php:184). Bootstrap runs four sequential scans plus a read of every non-terminal session (B/Domain/Session/SessionService.php:784-787,864-890): measured 0.4–0.6 s at 1M sessions. Device history too (B/Domain/Device/DeviceHistory.php:128-131,298-304): 106 ms and 85 ms.
7. **No reaper.** Sessions expire only when read by id (SessionService.php:339-363,400-443); lists show raw status. The participants' 20 s heartbeat is read by nothing. `leave` has no keepalive (W/services/api/client.ts:294). A crashed sharer's companion never leaves (D/src-tauri/src/companion.rs:257-259): DEVICE_BUSY for up to 60 minutes (B/Domain/Device/CompanionService.php:240-261). Slow polls overlap (useRemoteSession.ts:209,287); a relay restart makes every participant re-mint within a second (RemoteSignallingClient.ts:86).

## Checked and fine

- Idle tab: no timers on dashboard, devices or sessions pages; only /support polls.
- Poll lookups are indexed: measured 0.02–0.05 ms each; `pendingFor` 0.2 ms.
- Guests and devices never call the portal; Manage is off personal paths.
- Lists are capped (history and audit 100, devices 200, events and chat 200), except participants and invitations inside session detail.
- Cron does no full-table work.
- Device presence is timestamp-based; challenges and sign-in codes are swept on use.
- The ICE refresher never fires on schedule; stats are local.
